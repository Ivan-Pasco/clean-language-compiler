# ADR-0014 — Source text encoding and the remaining lexical questions

Once keywords were fixed as ASCII and string literals as full Unicode, thirteen dependent lexical questions were left open — source-file encoding, Unicode escapes, normalization, line endings, byte-order marks, digit character set, numeric separators, case sensitivity, comment nesting, method access on numeric literals, sign of negative literals, contextual keywords in name position, and triple-quoted strings. This ADR closes all thirteen; the substantive rules land in the language and platform chapters, and three of the questions turned out not to be lexical at all and produced a new platform chapter for text-file rules that five documents had each been asserting on their own.

---

## Context

A decision has been taken and is now written into [03 — Lexical Structure §Alphabet](../../04%20language/03-lexical-structure.md): **keywords and identifiers are ASCII; string literals and comments carry full Unicode.** Everything a machine must match exactly stays in one fixed vocabulary; everything written for humans is unrestricted.

That decision settles the alphabet of each category and leaves the mechanics around it open. They are collected here because they are interdependent — several cannot be answered without answering the others.

1. ~~**Source file encoding.**~~ **Resolved 2026-08-02.** Never stated anywhere. The `string` *type* is specified as UTF-8, but that is the runtime representation, not the encoding of a `.cln` file on disk. Without this, "string literals carry Unicode" has no mechanism. — Investigating this question showed it was not a language question at all: the same unowned assumption appeared in five documents across three trees, so the answer belongs to the ecosystem, not to the lexer. Fixed by [TXT-01..TXT-03](../../03%20platform/17-text-encoding.md) with diagnostic `CFG005`.
2. ~~**Unicode escapes.**~~ **Resolved 2026-08-02.** No `\u{...}` or `\uXXXX` form exists in the escape table. Combined with (1), there is currently no defined way to write a non-ASCII character other than embedding raw bytes in a file of unspecified encoding. — Closed as `\uXXXXXX`, six hexadecimal digits exactly, in the [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms) escape table. Fixed width rather than braced, because the delimiter only exists to disambiguate a variable count; six digits reach every code point, so no surrogate-pair form is needed and both surrogate halves and out-of-range values are rejected as `SYN005`.
3. ~~**Normalization.**~~ **Resolved 2026-08-02.** **Normalization.** No NFC/NFD rule for string comparison (identifiers are ASCII, so the question no longer arises there). This is observable, not academic: string equality is specified in the memory model as a byte comparison, so an NFC string and its NFD equivalent compare unequal. — Closed as byte-exact with no normalization anywhere: [TYP-07](../../04%20language/04-type-system.md#typ-07--string-equality-is-byte-exact-nothing-normalizes).
4. ~~**Line endings.**~~ **Resolved 2026-08-02.** **Line endings.** Carriage return is listed as whitespace, but nothing says whether `\r\n` terminates one line, whether a lone `\r` does, or whether a file must end in a newline — and indentation is significant, which makes line termination load-bearing. — Split in two: what the compiler reads is [LEX-07](../../04%20language/03-lexical-structure.md#lex-07--line-terminators), what the toolchain writes is [TXT-05](../../03%20platform/17-text-encoding.md#txt-05--a-tool-that-rewrites-a-file-preserves-its-line-terminators) and [TXT-06](../../03%20platform/17-text-encoding.md#txt-06--a-tool-that-creates-a-file-uses-the-projects-declared-convention-and-n-when-there-is-none).
5. ~~**Byte-order marks.**~~ **Resolved 2026-08-02.** Never mentioned. — Consumed when leading, never emitted, ordinary content anywhere else: [TXT-04](../../03%20platform/17-text-encoding.md#txt-04--a-leading-byte-order-mark-is-consumed-and-is-not-source-text).
6. ~~**Digit character set.**~~ **Resolved 2026-08-02.** **Digit character set.** Now settled for identifiers (ASCII `0-9`, per §Alphabet); still open for *numeric literals*, where a Unicode decimal digit could in principle be accepted. — Closed as ASCII only, in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms).
7. ~~**Numeric separators.**~~ **Resolved 2026-08-02.** **Numeric separators.** Whether `1_000_000` is legal is unstated in either direction. — Closed as not legal, in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms).
8. ~~**Case sensitivity.**~~ **Resolved 2026-08-02.** **Case sensitivity.** Never stated, though other chapters imply it. — Closed as case-sensitive everywhere: [LEX-08](../../04%20language/03-lexical-structure.md#lex-08--every-name-is-case-sensitive).
9. ~~**Comment nesting.**~~ **Resolved 2026-08-02.** **Comment nesting.** Whether `/* */` nests is undefined; `SYN004` (unterminated construct) exists but is not cited. — Closed as nesting, with the unterminated case citing `SYN004`: [LEX-09](../../04%20language/03-lexical-structure.md#lex-09--block-comments-nest).
10. ~~**Method access on a numeric literal.**~~ **Resolved 2026-08-02.** **Method access on a numeric literal.** `3.14.toInteger()` appears in the type system chapter. Since a leading dot is a legal float form, the lexer must decide whether `.toInteger` after `3.14` is a second literal or a member access. Unspecified. — Closed by a single condition in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms): a dot is part of a numeric literal only if a digit follows it immediately.
11. ~~**The sign of a negative literal.**~~ **Resolved 2026-08-02.** **The sign of a negative literal.** The chapter presents `-17` as a negative literal; the expression chapter makes unary `-` an operator. Under the second reading, the documented minimum of a signed 64-bit integer is unrepresentable as a literal. — Closed in favour of the expressions chapter: the sign is an operator ([LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms)), and the range is measured after it is applied ([TYP-01](../../04%20language/04-type-system.md#typ-01--the-core-types-and-their-ranges)).
12. ~~**Contextual keywords in name position.**~~ **Resolved 2026-08-02.** **Contextual keywords in name position.** A contextual keyword may be a variable name. Whether it may also name a function, a class, or a module is unstated. — Closed as yes, in every name position: [LEX-04](../../04%20language/03-lexical-structure.md#lex-04--the-reserved-words-are-a-disjoint-exhaustive-partition).
13. ~~**Triple-quoted string literals.**~~ **Resolved 2026-08-02.** **Triple-quoted string literals.** `"""…"""` is used in [21 — Block Handlers](../../04%20language/21-block-handlers.md) and defined in no literal table. — Defined in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms).

## Options considered

The remaining questions do not share one axis. Two shape everything else:

**Source encoding.** UTF-8 is the only serious candidate given that string literals and comments carry full Unicode; what needs deciding is whether it is *required* (a non-UTF-8 file is a lexical error) or merely *assumed*, and how a byte-order mark is treated.

**Normalization.** String equality is specified in the memory model as a byte comparison, so an NFC string and its NFD equivalent compare unequal today. The options are to leave it byte-exact and say so, to normalize literals at compile time, or to define a normalizing comparison — each observable, each with a different cost at the bridge.

The rest (line endings, comment nesting, method access on a numeric literal, the sign of a negative literal, numeric separators, the digit set inside numeric literals, case sensitivity) are ordinary lexer decisions with no deep tension; items 12 and 13 are surface questions that only need stating.

## Decision

**All thirteen questions closed 2026-08-02.** The keywords-ASCII / strings-Unicode decision is already written into the specification and is not reopened here.

**Question 1 — source file encoding: UTF-8, required, validated by the reader.** The decision is recorded in [03 platform / 17 — Text Files](../../03%20platform/17-text-encoding.md), not here, because it is not a lexical question: the same assumption was asserted independently by the memory model, the type system, the compiler, the semantic rules and the server library, and owned by none of them. Making it a rule of the lexical chapter would have created a sixth statement of the same fact.

Two things were settled that the question as posed did not anticipate. First, *required* rather than *assumed*: an unchecked encoding fails silently in production instead of loudly at build time, and validation costs one pass over bytes already being read. Second, the duty sits with whichever component reads the file, never with the compiler — the compiler receives text inside a JSON request document ([CMP-01](../../03%20platform/14-compiler-architecture.md#cmp-01--the-request-document-is-self-contained-the-compiler-touches-nothing-else)) and is structurally incapable of the check, because a file decoded with the wrong table yields text that is itself well-formed UTF-8 and undetectable from that point on.

Rejected: leaving the encoding *assumed*, which was the status quo and is what produced five orphan assertions; and placing the check in the compiler, which is where a reader would naively expect it.

**Question 13 — triple-quoted literals: multi-line, uninterpreted, margin set by the closing delimiter.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms). The form was already in use by [21 — Block Handlers](../../04%20language/21-block-handlers.md) and defined nowhere, so this question was not a design choice so much as a debt: the specification depended on syntax it had never written down.

The consequential part is the margin. Indentation is structure in Clean, and embedded text sits at whatever depth its enclosing code happens to have, so a literal that preserved every tab would hand its consumer content indented by an accident of the surrounding file. Tying the margin to the closing delimiter's indentation puts that choice on a visible line rather than in a heuristic. Leaving the content uninterpreted follows from the same use: the text carried is usually code, whose braces and backslashes belong to it.

Rejected: processing escapes and interpolation inside, which would consume the very content the form exists to transport; and permitting a single-line `"""` form, which would give the language two ways to write a one-line string for no gain.

**Question 12 — contextual keywords in name position: permitted everywhere.** Recorded in [LEX-04](../../04%20language/03-lexical-structure.md#lex-04--the-reserved-words-are-a-disjoint-exhaustive-partition). The reservation these words carry is positional — a word is a block header because a `:` follows it — so restricting them by the kind of thing being named would be an exception with nothing behind it. No ambiguity had to be traded away for it: a declaration names its type first, a class is introduced by `class`, and a block header needs its colon.

**Question 11 — the sign of a negative literal: an operator, with the range measured after it applies.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms) and [TYP-01](../../04%20language/04-type-system.md#typ-01--the-core-types-and-their-ranges). This question was a genuine contradiction between two Accepted chapters rather than a silence, so closing it meant choosing which one was wrong; the lexical chapter was.

Both readings can produce the documented minimum — under a sign-bearing literal the value is direct, and under an operator it is reached by measuring the range after the sign applies. The tiebreak was elsewhere. Folding the sign into the literal requires distinguishing `a - 1` from `a` followed by `-1`, and the only two mechanisms for that each contradict an existing Accepted rule: spacing-sensitive meaning contradicts [LEX-01](../../04%20language/03-lexical-structure.md#lex-01--indentation-is-one-tab-per-level)'s allowance of spaces inside expressions, and a parser-directed lexer contradicts the compiler's pass-purity contract ([Platform 14 §14.4.1](../../03%20platform/14-compiler-architecture.md#1441-pass-contracts)). Unary minus is also required for `-x` under either reading, so the sign-bearing literal adds a meaning rather than removing one.

Left open deliberately: no diagnostic is registered for a literal outside its type's range. That gap belongs to [ADR-0019](0019-precision-modifiers.md), which already records it; inventing a code here would have been a new class of failure outside any ADR ([ERC-03](../../03%20platform/09-error-codes.md#erc-03--registration-process)).

**Question 10 — the dot after a numeric literal: it belongs to the number only before a digit.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms). The question named one case, `3.14.toInteger()`, but the same condition settles four: the leading-dot form `.5`, member access on an integer literal, member access on a float literal, and whether `3.` is a float without a fractional part. It is not, and that falls out rather than needing to be decided — which is why no separate rule states it.

**Question 9 — comment nesting: they nest.** Recorded in [LEX-09](../../04%20language/03-lexical-structure.md#lex-09--block-comments-nest). The decisive consideration is that the failure mode of non-nesting lands on the principal use of a block comment — disabling a region while working — and lands hardest on well-documented code, since a region is more likely to contain a comment the better it is written. The resulting syntax error also appears at an unrelated location, so the developer is not led back to the cause. Writing the rule also gave `SYN004` its first citation: the code was registered and no chapter pointed at it.

Rejected: C's non-nesting behaviour, whose known workaround is to advise developers not to use the construct for its main purpose.

**Question 8 — case sensitivity: case-sensitive, everywhere.** Recorded in [LEX-08](../../04%20language/03-lexical-structure.md#lex-08--every-name-is-case-sensitive). Of the thirteen this is the one that was purely unwritten rather than genuinely undecided: two Accepted rules already presumed the answer, so the alternative was not available without amending them. Nothing was chosen here that the specification had not already committed to; it was stated and given an ID so it can be cited and checked.

**Question 7 — numeric separators: not legal.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms). This is the one question of the thirteen decided on reversibility rather than on merit: separators are a readability gain with no cost of principle, and the argument for refusing them now is that the refusal can be undone and the acceptance cannot. A second consideration reinforced it — accepting an underscore obliges the specification to say whether it may lead, trail, double, sit beside the decimal point, appear inside a hexadecimal prefix or inside an exponent, and an unanswered one of those is a silent divergence between implementations.

Rejected: accepting `1_000_000` now, which would have been defensible had the placement rule been written in full at the same time.

**Question 6 — digit character set: ASCII only.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms). It is [LEX-02](../../04%20language/03-lexical-structure.md#lex-02--keywords-and-identifiers-are-ascii-text-is-unicode) applied to numbers rather than a new principle: a numeric literal is something a machine must recognise exactly, so it stays in the fixed ASCII vocabulary, while text shown to a user remains unrestricted because it is a string.

Rejected: accepting Unicode decimal digits, which would require the lexer to carry the Unicode character database to read an integer, would raise the question of what a literal mixing scripts means, and would allow a literal that renders as `42` in a reviewer's font to hold another value.

**Question 5 — byte-order marks: consumed when leading, never emitted.** Recorded in [17 §17.5](../../03%20platform/17-text-encoding.md#175-byte-order-marks) alongside question 1, for the same reason: a mark is consumed before the lexer runs, so the rule binds every component that reads a file. Of the three available behaviours, treating the mark as content is the only one that produces an undiagnosable failure — an invisible character fused to the first token of a file that looks correct — and rejecting it produces an error about bytes the developer cannot see. Positions are measured from the byte after the mark, so a file with one and a file without one report every diagnostic identically.

**Question 2 — Unicode escapes: six hexadecimal digits, fixed width.** Recorded in [LEX-06](../../04%20language/03-lexical-structure.md#lex-06--literal-forms), which is genuinely lexical and stays in the language tree.

The question was posed as a choice between the four-digit form and the braced variable-length form. It is really a choice between *fixed* and *variable* width: hexadecimal digits include `a`-`f`, so a variable-length escape cannot be told apart from the text that follows it, and the braces exist only to mark where the number ends. At a fixed width no delimiter is needed at all. Six digits is the width of the largest code point that exists, so the escape reaches every character, no surrogate-pair form is required, and the failure mode that ADR-0010 is still open about — a surrogate half arriving alone — cannot be written in the first place.

**Question 4 — line endings: both accepted, normalised on read, preserved on write.** This question, like 1 and 5, turned out to have two halves in two components. The compiler's half is [LEX-07](../../04%20language/03-lexical-structure.md#lex-07--line-terminators): `\n` and CRLF both terminate a line and are normalised before indentation is measured, a lone carriage return is `SYN001` rather than whitespace, and no final terminator is required. Writing `LEX-07` exposed a defect in `LEX-01`, which listed carriage returns as whitespace and so made an invisible stray one legal inside significant indentation.

The toolchain's half is [TXT-05](../../03%20platform/17-text-encoding.md#txt-05--a-tool-that-rewrites-a-file-preserves-its-line-terminators) and [TXT-06](../../03%20platform/17-text-encoding.md#txt-06--a-tool-that-creates-a-file-uses-the-projects-declared-convention-and-n-when-there-is-none), and it exists because the ADR framed this as a lexer question when the system also *writes* text. A tool that normalised terminators while editing one line would produce a whole-file diff; tools therefore detect a file's convention on read and reproduce it on write, exactly as editors have always done. For a file being created there is nothing to detect: `.editorconfig` decides, `\n` otherwise, and never the host platform — deriving it from the operating system would make one command produce different bytes for different members of a mixed team. Scaffolding writes the `.editorconfig` so the choice is a visible, changeable line in the repository.

Rejected: requiring a single convention in the compiler, which is unenforceable because git converts terminators on checkout without asking and neither editor nor git tells the developer; treating a lone carriage return as whitespace, which is the status quo and lets an invisible character alter block structure; and choosing the creation default from the host platform.

**Question 3 — normalization: none, and equality is byte-exact.** Recorded in [TYP-07](../../04%20language/04-type-system.md#typ-07--string-equality-is-byte-exact-nothing-normalizes). The premise stated in this ADR — that the memory model already specifies a byte comparison — turned out to be a generous reading: that document said comparison uses "(length, payload)" and never said whether the payload comparison normalizes, so the question had no answer anywhere rather than a weak one. It now says byte-exact and cedes the observable rule to the language tree.

Rejected: normalizing literals at compile time, which makes the compiler rewrite a value the developer wrote, so a string leaves the source file different from how it entered; and a normalizing `==`, which charges every string comparison in the language and every crossing of the host bridge for a case that appears rarely. Both would also have required amending an Accepted representation rule, where the chosen option only required stating it precisely. The accepted cost is real and is written into TYP-07 with a worked example: two strings that look identical can compare unequal, and a program that needs canonical comparison must ask for it explicitly.

Rejected: the four-digit form, which reaches only the basic plane and would have left invisible characters above it unescapable, and would have required the specification to explain a Unicode plane boundary to justify the limit; and the braced form, which spends a delimiter on an ambiguity that a fixed width does not have, and would have needed an extra rule to keep that brace from opening a string interpolation.

## Consequences

The thirteen questions are closed and this ADR is settled; the rules themselves live in the specification, not here.

Three of the thirteen turned out not to be lexical at all. Source encoding, byte-order marks and half of the line-ending question bind every component that reads or writes a file, not the lexer, and they created [03 platform / 17 — Text Files](../../03%20platform/17-text-encoding.md) as the home of a fact that five documents had each been asserting on their own. That the ADR framed them as lexical is the most useful thing it recorded: the question a document asks can be scoped more narrowly than the answer it needs.

Closing the list also surfaced defects that no question had named. `LEX-01` listed carriage returns as whitespace, which made an invisible one legal inside significant indentation. `LEX-03` carried a note calling its own character set undecided, contradicting the two rules above it. §14.1.1 of the compiler asserted an encoding with no guarantor and no diagnostic. The error-code registry's own count was stale by seventeen codes. *Literal* — the subject of `LEX-06`'s title — had no glossary entry. Each was repaired in the change that met it.

One gap is deliberately left open and belongs elsewhere: no diagnostic is registered for a numeric literal outside its type's range. [ADR-0019](0019-precision-modifiers.md) already records it, and inventing a code here would have created a class of failure outside any ADR ([ERC-03](../../03%20platform/09-error-codes.md#erc-03--registration-process)).
